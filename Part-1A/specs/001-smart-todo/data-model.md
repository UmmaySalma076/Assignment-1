# Data Model: Smart Todo Application

## Overview

The feature uses a single persisted entity, `Task`, to represent a todo item. The model is intentionally small and aligned to the specification: each task has a unique identifier, a required title, an optional description, a completion flag, and a system-generated creation timestamp. No completion-history model is required in v1.

## Entity: Task

| Field | Type | Constraints | Notes |
|-------|------|-------------|-------|
| id | integer | primary key, auto-increment | Unique task identifier stored in SQLite |
| title | string | required, 1-100 chars after trim | Must be non-empty after trimming whitespace |
| description | string or null | optional, max 1000 chars after trim | May be omitted or empty |
| completed | boolean | required, 0 or 1 in SQLite | Represents pending/complete state |
| created_at | string | required, ISO 8601 timestamp | Generated by the application at creation time |

## Relationships

- A task exists independently and does not require relationships to other entities for the v1 scope.
- The task collection is the set of all persisted tasks in the SQLite database.
- Task retrieval and update operations are keyed by `id`.

## Validation rules retained from specification

- Title is required and cannot be empty after trimming.
- Title length must be <= 100 characters.
- Description, if present, must be <= 1000 characters.
- Completion state is persisted as a boolean-compatible value.
- Creation time is generated by the application and stored in a timestamp format consistent with the API contract.

## State transitions

The task lifecycle is straightforward:

- Created: `completed = false`, `created_at` set at creation
- Pending: `completed = false`
- Completed: `completed = true`
- Deleted: row removed from the tasks table

There is no v1 requirement to retain historical task status changes beyond the current saved state.

## SQLite schema

```sql
CREATE TABLE tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL CHECK(length(trim(title)) > 0),
    description TEXT,
    completed INTEGER NOT NULL CHECK(completed IN (0, 1)),
    created_at TEXT NOT NULL
);
```

## Ordering and determinism

- Listing tasks must have a stable deterministic order, defined as ascending `id`.
- This ordering is independent of clock time and supports consistent test expectations.
- Equivalent valid input sequences against the same database state should yield equivalent list order and API responses.
